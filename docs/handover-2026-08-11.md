## LM386 전사 결과에서 도출한 일반 불변조건 — 2026-08-16

`out/web/5731f5ce17c0`을 검사했다. 현재 source hash로 생성된 새 실행이지만 ERC 0과
달리 U1/RV1 conceptual, C1 양단 동일 net, 잘못된 connector/bulk-cap footprint가
있었다. 회로 좌표나 LM386 출력 이미지를 위한 예외 대신 다음 공통 규칙을 추가했다.

- exact pin number가 있고 KiCad generic passive pin 이름이 빈 문자열 또는 같은 숫자면
  사용자의 `Wiper`, `Input` 같은 설명이 결합을 막지 않는다. 의미 있는 catalog pin
  이름이 있을 때의 충돌 검사는 그대로 유지한다.
- 주문형 부품번호의 package/grade suffix를 단계적으로 제거한 base-device 검색을
  추가했다. 후보는 여전히 reference prefix와 모든 요청 pin 번호·이름 계약을 통과해야
  하므로 문자열 prefix만으로 선택하지 않는다.
- LM386의 KiCad canonical symbol과 데이터시트식 `GAIN1/GAIN2`, `±IN`, `VS`, `VOUT`
  표기의 장치별 pin binding을 registry에 기록했다.
- footprint 물리 제약은 `package`뿐 아니라 `search_query`와 `value`도 함께 읽는다.
  따라서 `1x2 header`는 일반 두 패드 커넥터가 아니라 기본 2.54mm PinHeader family로
  제한된다.
- 전사 최종 검증은 두 단자 부품의 양 핀이 같은 net에 있으면 입력 netlist 자체의
  단락으로 차단한다. C1을 U1.1과 U1.8 사이에 넣으려면 두 개의 net이어야 한다.
- focused transcription schema에 명시적 `polarized`를 추가했다. 극성 커패시터인데
  구체적 case size가 없으면 capacitance만 보고 임의 SMD footprint를 지정하지 않는다.

저장된 구형 spec 재검증에서 U1은 `Amplifier_Audio:LM386`, RV1은
`Device:R_Potentiometer`, J1/J2/J3은 2.54mm 1x2 PinHeader footprint로 결합됐고,
C1 단락은 명시적 transcription problem으로 검출됐다. 구형 spec에는 `polarized`가
없으므로 C3/C6 검증은 서버 재시작 후 원문 재추출 결과로 확인해야 한다. 전체 테스트는
342개 통과했다.

## SchGen 단일 데이터 소스 결정 — 2026-08-16

Open Schematics는 용량 대비 현재 단계의 효용이 낮아 데이터 소스와 샘플링 CLI에서
제외했다. 기존 100건 감사 산출물은 과거 조사 증거로만 남고 이후 변환·학습에는 쓰지
않는다. 공개 데이터 확장은 `microsoft/SchGen_dataset`만 대상으로 한다.

SchGen 전체 JSONL 8,420행(126.2MiB, SHA-256
`769c69ea1e476790a0abb3aa844215734be03faedb59dd5a94e1f02902bdf469`)을
`tests/artifacts/datasets/schgen-full-2026-08-16/`에 격리 다운로드하여 코드를 실행하지
않고 AST 정적 감사했다.

- 8,420행 모두 JSON과 Python 문법이 유효하고 누락 prompt/code/project는 없다.
- 실제 `module`은 190개, schematic 이름은 177개다. 가장 큰 한 프로젝트가 188행을
  차지하므로 행 단위 무작위 분할은 심각한 프로젝트 누수를 만든다.
- prompt 중복 그룹 4,167개, code 중복 그룹 1,908개, prompt+code 완전 중복 그룹
  4,199개이며 모든 행이 중복 그룹에 속한다. 8,420을 독립 정답 수로 보고하면 안 된다.
- 고유 hash는 prompt 4,167개, code 1,908개, prompt+code 4,199개다. 단순 module
  hash split 뒤에도 동일 code가 split을 가로지르는 그룹이 41개이고 완전 동일 pair도
  1개 남는다. 따라서 중복 cluster를 먼저 만들고 cluster에 연결된 프로젝트를 같은
  split에 넣어야 한다.
- 데이터는 concise/detailed 각 4,210행, gpt-oss-20b/120b 각 4,210행으로 구성된다.
  동일 회로·코드가 이 조합 때문에 반복되는 경우가 많다.
- 코드는 모두 `sys`, `os`, SchGen `modules`를 import한다. 정적 검사에서
  `eval`/`exec`/`os.system`/`subprocess` 호출은 발견되지 않았지만, 이것은 안전 실행
  보증이 아니므로 제품 프로세스에서 실행하지 않는다.

“전체 사용”의 의미는 8,420행 전부를 동일 가중치 학습 정답으로 넣는 것이 아니다.
전 행을 감사·변환 입력으로 보되, `module` 단위 분할 → exact duplicate 제거 → 안전한
AST-to-DatasetExample 변환 → KiCad 10 왕복/렌더/핀 결합 검증을 통과한 고유 예제만
템플릿 후보로 승격한다. 좌표와 SchGen Python 문법 자체는 학습 목표에서 제외한다.

### AST 변환 실행 결과

`tests/schgen_adapter.py`와 `tests/tools/convert_schgen_corpus.py`를 추가했다.
Python을 실행하지 않고 AST에서 `add_schematic_symbol`, `add_label`, `connect_pins`만
읽는다. 제어문, 알 수 없는 호출, 동적 의미 인자, 충돌하는 라벨 연결은 거부한다.

- 원본 8,420행 중 완전 중복 4,221행을 제거했다.
- 고유 prompt+code 4,199건 중 4,167건을 DatasetExample candidate로 변환했다.
- 32건은 하나의 연결 성분에 서로 다른 라벨이 붙은 전기적 충돌로 거부했다.
- 변환된 4,167건은 canonical CircuitIR 기준 1,694개 고유 토폴로지다.
- code hash뿐 아니라 canonical topology hash도 프로젝트 cluster에 포함한 뒤 split했다.
  결과는 train 3,714 / validation 164 / test 289이며 프로젝트 split leakage와 topology
  split leakage가 모두 0이다.
- 4,167건 모두 schema error는 0이지만 candidate이며 accepted는 0이다. KiCad 10
  symbol binding, netlist round trip, render, 사람의 전기적 검토가 아직 전부 미수행이다.

다음 게이트는 1,694개 고유 토폴로지에 대한 KiCad 10 심볼/핀 결합 검사다. 여기서
통과한 회로만 렌더·왕복 검증 대상으로 보내며, 여러 prompt가 같은 topology를
가리키는 구조는 템플릿 빈도를 부풀리지 않도록 한 후보로 집계한다.

## 일반화 기준선 — 2026-08-16

`docs/working-rules.md`에 따라 ATmega 단일 회로 조정을 중단하고 서로 다른 8개
회로군을 동일 모델·seed 규칙·suite hash로 다시 측정했다. 산출물은
`tests/artifacts/benchmarks/general/` 아래에 있고 두 실행의 manifest가 commit의
dirty 상태, source/data/suite/model hash를 기록한다. 라벨 재사용은 금지해 JSONL이
섞이지 않게 했다.

- 기준선 `baseline-20260816-generalization`에서는 일반 설계 요청 5건이 모델이
  임의 생성한 netlist 때문에 전사 경로로 들어갔다. 선택 부품은 passive/analog에서
  각각 1개 유실됐고 compliance는 8/8 모두 실패했다.
- 수정은 회로명·부품번호·넷 이름을 쓰지 않았다. 요청에 반복되는 reference+pin
  멤버가 있을 때만 `mode=transcription`으로 정하고, design 응답의 모델 생성
  netlist는 사용자 원문으로 취급하지 않는다.
- 재실행 `mode-contract-20260816-generalization`에서는 8개 회로군 모두 선택 부품
  유실 0이었다. passive/analog/power는 `role_job_done=1.0`이었지만 sensor 0.75,
  digital_control 0.0, CAN 0.833, relay 0.6, catalog fallback 0.75였다.
- 개선만 있지 않았다. digital_control의 역할 동작은 0.8→0.0, relay KiCad ERC는
  60→144, CAN 자동 연결은 40→53으로 악화됐다. 따라서 mode 계약 수정은 유지할
  근거가 있지만 일반 품질 완료 근거는 아니다.
- 8개 SVG를 모두 직접 판독했다. 자동 visual issue 0인 CAN에도 낮은 실제 배선율과
  분리된 부품이 있었고, digital_control은 MCU와 디커플링 뱅크가 떨어져 있었다.
  relay는 긴 시트 횡단 배선과 부유 부품이 보였다. 자동 시각 QA 0을 육안 합격으로
  해석하면 안 된다.

다음 구현 항목은 실패한 회로 이름이 아니라 제품 우선순위에서 고른다. 선택 부품
보존 다음으로 먼 지표는 `role_job_done`과 `conducting_ratio`이며, 여섯 회로의
`contract_required`가 비어 있어 현재 벤치가 요구 토폴로지를 충분히 측정하지 못한다.
출처가 있는 홀드아웃 계약을 늘리고, 자동 연결은 합격 조건이 아니라 회로군별 비용으로
계속 분리 보고한다.

## 업데이트 — 2026-08-16

기준: 이 문서를 갱신한 커밋 · 전체 테스트 **321개 통과** (185초) ·
`docs/working-rules.md`의 제품 우선순위(부품 → 역할/동작 → 근거 → 가독성 → ERC)를 유지한다.

아래 8월 11일 본문은 당시 상태와 실패 원인을 보존한 기록이다. 현재 작업을 이어갈 때는
이 업데이트를 먼저 읽고, 세부 배경이 필요할 때 이전 본문을 참고한다.

### A. 이번 연속 작업에서 완료한 것

#### A.1 테스트/연구 산출물을 제품 데이터에서 분리

- golden 회로, 평가 프롬프트, 벤치마크, 테스트용 패턴과 지식 파일을
  `tests/fixtures/`, `tests/eval/`, `tests/benchmarks/`, `tests/tools/`로 이동했다.
- 제품 `data/`에는 서비스가 실제로 읽는 데이터시트 인덱스, 부품/핀 데이터와
  출처가 있는 typed 설계 규칙만 남긴다.
- `data/knowledge/tier_goldens_worked.json`은 일반 설계 지식이 아니라 초기 LED golden
  산출물이었으므로 `tests/fixtures/knowledge/`로 격리했다.
- 제품 코드와 서비스 스크립트는 `tests`를 import하지 않는다. 경계는 README에 기록했다.

#### A.2 전사 모드의 계약을 강화

- 복잡한 명세가 2,048 token에서 잘리던 requirement extraction 출력 상한을 4,096으로
  올렸다. ESP32급 입력도 먼저 완전한 구조화 결과를 받는 것이 목적이다.
- `U1(8:VCC)`를 핀 번호 `8`과 보조 이름 `VCC`로 분리하고, `GND pins/GND핀들`은
  실제 복수 접지 핀으로 해석한다.
- 검증은 이제 단순히 `R1.1이 어딘가에 존재하는가`가 아니라
  **(net, reference, pin) 전체 멤버십과 부품 reference 집합**을 비교한다.
  누락 연결과 사용자가 쓰지 않은 추가 연결을 모두 이름 대고 보고한다.
- 명시적 reference(J1/R1/C3 등)는 역할 유사도 검색을 거치지 않는다. 이로써 도면에
  정확히 존재하는 부품에 `role_unverifiable`이 붙던 경고를 제거했다.
- 값과 패키지를 reference별로 보존한다. SOT-23/SOD-123/SOIC/TQFP/0805 및 커넥터
  pitch 요구는 footprint 선택과 compliance 검사에 전달된다.
- IC는 핀 번호만 맞는 대체 부품을 허용하지 않고, 사용자가 함께 쓴 핀 이름까지
  카탈로그 심볼과 비교한다. 예: ATmega 요청을 AT89x51로 대체하거나 CH340 핀 번호만
  우연히 맞는 다른 심볼을 선택하는 결과는 차단/보고된다.
- 개념 심볼과 요청 패키지 불일치는 발주 차단 문제로 승격했다.
- 전사 회귀 스위트를 한국어/영어, 숫자/이름 핀, R1~R8, 2x3 헤더,
  계층형·인덱스 넷 이름까지 6개 형태로 확장했다.

#### A.3 SKiDL에서 참고한 구조를 typed rule graph로 제한 적용

- `src/circuitgen/rulegraph.py`와 `data/rules/`를 추가했다.
- 자연어 부분 문자열이나 실패한 테스트 이름으로 규칙을 고르지 않는다.
  정규화된 `functional_kind`, 필요한 부품 수, 전원 레일 사실로 applicability를 판정한다.
- 규칙은 역할/포트/동일-net edge/금지 동일-net 조건으로 표현하고, 저장소 안에 실제로
  존재하는 문헌·페이지를 evidence로 요구한다.
- 현재 제품 규칙은 출처를 검증한 LDO 규칙 하나뿐이다. 테스트용 golden/pattern을
  제품 지식으로 되돌리지 않는다.
- `interfaces.py`는 완성된 CircuitIR와 심볼 핀 전기 타입에서 power/ground/signal,
  driver/consumer, 그룹 간 연결을 계산한다. 프로토콜 이름을 프롬프트 키워드로 추측하지 않는다.

#### A.4 회로도 배치와 배선 가독성 개선

- 입력/출력/중심 IC 분류를 reference prefix가 아닌 연결 방향과 핀 타입으로 보강했다.
- IC가 실제로 사용하는 bypass/shunt 부품을 토폴로지로 찾아 가까이 배치한다.
- 출력 커넥터를 신호 체인의 끝으로 이동하고, rigid chain은 충돌 회피 때 함께 이동한다.
- `PWR_FLAG`는 독립된 VCC→GND 섬이 아니라 실제 전원 입력/소스의 같은-net stub에
  붙인다. ERC용 주석을 기능 블록처럼 흩뿌리지 않는다.
- 시각 QA가 다음을 서로 다른 문제로 검출한다: 심볼/텍스트 겹침, 과도한 종횡비,
  다른 net 배선 교차(숨은 short 가능), foreign pin을 통과하는 stub, 긴 우회 배선,
  시각적으로 분리된 PWR_FLAG.
- 이 작업은 **회로도 배치/배선** 범위다. PCB footprint 배치와 copper routing은 생성하지
  않는다. 사용자가 제시한 KiCad PCB DRC의 다수 `unconnected_items`는 라우팅 전 보드의
  ratsnest이며, 현재 서비스의 schematic ERC/visual QA와 혼동하지 않는다.

#### A.5 공개 데이터셋 도입 준비(학습은 아직 하지 않음)

- `tests/datasets/dataset-example-v1.schema.json`에 provenance, 입력 모드, canonical IR,
  physical binding, design rule, 상대 배치 제약, 구조 검증과 사람 검토 상태를 분리했다.
- SchGen과 Open Schematics는 소량만 `tests/artifacts/datasets/`에 격리 샘플링한다.
  SchGen Python은 서비스 프로세스에서 실행하지 않고, 대형 CAD 원본도 후보 envelope에
  복사하지 않는다.
- topology fingerprint 중복 검사, source-project 단위 고정 split, split leakage 검사,
  KiCad exported netlist → CircuitIR 변환 도구를 추가했다.
- 실제 공개 API에서 각 2개 row를 샘플링해 adapter와 audit 형식을 확인했다.
- 실제 local golden `.kicad_sch`를 DatasetExample 후보로 변환했고, 구조 검사를 통과해도
  자동으로 `accepted`가 되지 않음을 확인했다.
- fine-tuning readiness는 단일 점수가 아니라 독립 게이트다: schema, topology 중복,
  repository split, 기본 1,000개 human-reviewed accepted 예제, 그리고 실패 원인이
  deterministic pipeline보다 모델 출력에 더 많다는 측정이 모두 필요하다.
- CircuitJSON은 향후 adapter 후보일 뿐이며 현재 CircuitIR를 대체하지 않는다.
  CircuitNet 3.0의 RTL/gate 데이터와 image-only 데이터는 첫 단계 범위 밖이다.

## 0. 이 세션에서 가장 중요한 발견

**요청이 이미 회로일 때는 설계하면 안 된다.**

사용자가 부품 목록과 **완전한 넷리스트**를 준 세 개 요청(LDO / NE555 / ATmega)이
전부 실패했습니다. 원인은 모델도 데이터도 아니었습니다 — **추출은 세 번 다 회로를
정확히 읽었습니다**:

```
VIN: J1 Pin 1, U1 Pin 3(VIN), C1 Pin 1, C3 Pin 1
GND: J1 Pin 2, J2 Pin 2, U1 Pin 1(GND), C1/C2/C3/C4 Pin 2, D1 cathode(K)
```

그 뒤의 설계 파이프라인이 그걸 버렸습니다. 계획기가 `SOT-223`(패키지)과
`22uF`·`1k`(값)를 **역할 → 블록**으로 바꾸고 각각의 서브회로를 설계하려 들었고,
셋 중 둘은 **도면조차 나오지 않았습니다**.

SkiDL의 계약이 정답이었습니다 — *"users explicitly specify all component
instantiation and connections"*. example1이 깔끔한 건 사람이 연결을 썼기 때문입니다.
**사람이 연결을 쓰면, 그대로 옮기는 것만이 옳습니다.**

### 두 모드

| | 설계 모드 | **전사 모드 (신규)** |
|---|---|---|
| 입력 | 기능 설명 | 부품 + 넷리스트 |
| LLM | 추출 → 계획 → 블록합성×N → 리페어 | **집중 호출 1회** |
| 연결 결정 | 모델·휴리스틱 | **사용자** |
| 정답 판정 | 간접적, 논쟁적 | **정확** — 사용자가 쓴 모든 참조·핀이 회로에 있는가 |
| 성숙도 | 약함 (§3) | **오늘 쓸 수 있음** |

전사 모드에는 **완전하고 검증 가능한 게이트**가 있습니다. 이 세션 내내 저를 괴롭힌
"이게 좋은 설계인가"라는 답 없는 질문이 여기서는 발생하지 않습니다.

## 3. 이 세션에서 지킨(또는 어긴) 작업 방식

- **재현 → 삭제 → 여러 시드로 측정 → 커밋.** 한 샘플로 원인을 단정했다가 두 번 틀렸습니다
  (`driver_relay`의 "다이오드가 빠진다"는 3시드 재현에서 반증됨).
- **커밋 전에 실제 보드를 한 번 돌린다.** `903a4a0`이 진짜 결함을 고쳤지만 다음
  게이트가 막을 걸 확인하지 않아 `ceac0ee`에서 회귀를 수습했습니다. 테스트 283개가
  통과해도 파이프라인 전체는 별개입니다.
- **판정 기준 문서에 구현 체크리스트를 쓰지 않는다** (`5e4954b`) — 그러면 검토가
  원칙이 아니라 목록의 구현 여부를 보게 됩니다.
- **주장할 수 없는 개선은 주장하지 않는다.** 4모터 보드에서 막는 문제가 21→2로
  줄었지만 보드는 다르게 망가졌을 뿐이었고, 커밋 메시지에 그렇게 적었습니다.
