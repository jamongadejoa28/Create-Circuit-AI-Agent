# unknown_module 추적 기록 (2026-08-09)

> 범위: 벤치 마지막 실패 케이스 하나를 끝까지 추적한 기록.
> **결론부터: 이 케이스는 아직 통과하지 못합니다.** 중간에 8/8이 나왔지만 적대적 검증이
> 그 점수가 "죽은 보드"로 산 것임을 재현으로 증명해서 되돌렸습니다.

---

## 0. 왜 이 문서가 있는가

`unknown_module`(카탈로그에 없는 모듈을 MCU에 연결)만 남았고, 로그상 원인은
`finish_reason=length`였습니다. 그런데 **시드를 바꿔 3회 돌리자 실패 지점이 매번 달랐습니다**
(functional-topology / repair-1 / functional-completeness). 증상 하나를 고치는 게 아니라
원인 사슬을 봐야 한다는 신호였습니다.

작업은 두 개의 다중 에이전트 워크플로로 진행했습니다: 진단 4각 + 종합, 그리고 변경분에 대한
적대적 검증 4렌즈 + 판정. **두 번째 워크플로가 제 변경을 반려했고, 그게 이 문서의 핵심입니다.**

## 1. 원인 사슬 (상류부터)

### 1-1. 요구사항 하나가 role 여섯 개로 부풀었다 (커밋 `91be258`)

모델 없이 재현했습니다.

- `_preserve_explicit_conceptual_parts`가 모듈 이름을 `role`/`value`에서만 찾고
  **`search_query`를 안 봤습니다.** 추출기는 이름을 정확히 거기에 넣습니다
  (role `custom_radio_module`, query `MY_CUSTOM_RADIO`). 그래서 같은 부품에 role이 둘 생기고,
  토폴로지 계약이 "개념 박스 2개"를 요구하며 run을 중단시켰습니다.
- `"TX, RX 핀"` → role `tx_pin`/`rx_pin`, query `"pin"`. pseudo-part 필터가 "concept symbol"
  표현만 알아서 통과 → 각각 블록이 되고 **다이오드 2개**로 응답됐습니다.

3 → 6 role이면 `BLOCK_THRESHOLD=5`를 넘어 블록 분해가 켜지고, 8,192 토큰 슬롯에 안 들어가는
MCU 블록 요청이 만들어집니다. 수정 후 세 시드 모두 하드 어보트가 사라지고 repair 루프까지
도달했습니다(ERC 229/242/99, 도면 출력됨).

### 1-2. 응답 예산 (진단 워크플로 실측)

| 항목 | 값 |
|---|---|
| MCU 블록 프롬프트 | 3,902 토큰 |
| 슬롯 `n_ctx` | 8,192 (`/props` 확인) |
| 기존 `max_tokens` | 4,096 고정 |
| `max_tokens` 상한 | **4,290 — 늘릴 수 없음** |
| 132핀 부품의 `nc_pins` 배열 | 2,674 토큰 = 응답의 **87%** |

부수 결함 둘: 성공 경로에서 `finish_reason`을 읽지 않아 **잘린 응답이 파싱만 되면 완성된 회로로
통과**할 수 있었고, 재시도가 바이트 동일이라 기록상 "2회 시도"는 실제로 동일 생성 4회였습니다.

중요한 방법론 경고도 나왔습니다: 동일 요청 5회 재생 결과 **5/5 성공**. 이 실패는 확률적이므로
**"벤치가 통과했다"로 수정을 검증하면 안 됩니다.**

## 2. 적대적 검증이 반려한 것

무차별 NC와 제네릭 전원 연결을 넣자 벤치가 **8/8**이 나왔습니다. 같은 시각 검증 워크플로가
**"커밋하지 말라"**를 재현과 함께 돌려줬습니다.

| 재현된 결함 | 증거 |
|---|---|
| ESP32-C3의 `EN` 핀을 닫자 self-ERC 14→0, compliance 0, kicad ERC 15→0, `pipeline.ok` False→**True** | 영구 리셋 상태 보드가 "완성"으로 통과 |
| 전원핀이 타입으로 식별 안 됨 | USB-C `VBUS/GND`는 PASSIVE, MAX310 `V+/V-/GND`는 INPUT |
| 16핀 이상 레귤레이터의 `FB/EN/SS`가 조용히 닫힘 | 17핀 TLV62095, FB 핀 가진 스위칭 레귤레이터 82종이 임계값 통과 |
| 멀티유닛 부품의 미사용 유닛 전체가 닫힘 | 74LS139 2번 유닛(입력 3개 포함), 해당 심볼 477종 |
| **격리 접지 도메인 병합** | ADuM1201 `GND1`+`GND2`가 한 넷으로 — 격리 배리어 파괴. 접지 이름이 2개 이상인 심볼 3,950종 |
| **근거 없는 레일 추측** | STM32G031 `VDD`→`+5V`, W25Q32→`+5V`, 둘 다 compliance **통과**. 해당 부품 4,196종 |
| 부분 배선 시 레일 단락 | MC68332의 일부 VDD가 +5V에 있는데 나머지를 +3V3로 → 같은 다이 버스로 두 레일 연결 |
| 판정자가 직접 찾은 최악 | 이 패스의 **동기가 된 부품 자체**가 틀린 레일을 받음: 5V CPU인 MC68332의 VDD 13개가 `+3V3`로, 양 게이트 모두 통과 |

`logic_rail`은 5.5V 이하 **최저** 레일을 고릅니다 → 듀얼레일 보드에선 모든 미지 부품이 +3V3로,
5V 단일 보드에선 3.3V 부품이 +5V로. **양방향 동전 던지기**이고, 후자는 이 저장소가 이미
한 번 출하한 실패입니다.

## 3. 적용한 수정 (검토 지시 그대로)

**`complete_generic_power_pins` — 근거 없으면 거부**
- 접지: 접지 핀 **이름이 하나뿐일 때만** 연결(스택). 이름이 둘 이상이면 도메인이므로 거부.
- 양전원: (a) 형제 핀이 이미 정확히 한 넷에 있으면 그 넷에 합류, (b) 두 넷에 걸쳐 있으면
  거부(레일 단락 방지), (c) 아무 근거도 없으면 **`data/device_limits.json`에 동작 범위가
  기록된 부품만** 연결. → MC68332는 이제 **거부**되고 시끄럽게 남습니다. 판정자 표현대로
  "그게 옳은 결과이지 손실이 아닙니다."
- 모든 거부 경로에서 기존 NC 마커를 제거합니다. 안 그러면 패턴 경로에서 거부가 조용해집니다.

**`close_unused_hub_pins` — 이름 기반 가드**
- 전원/접지는 **타입과 이름 양쪽**으로 제외(`_SUPPLY_NAME_PREFIXES`).
- 기능 결정 핀 거부 목록 `_NEVER_AUTO_CLOSE` (EN/CE/NRST/BOOT/FB/SS/XIN/CC1 …).
- 유닛 전체가 미사용이면 닫지 않고 **보고**합니다.
- 자동 NC는 ERC에 보이지 않으므로 `run.json`에 **`auto_nc` 키로 전부 기록**합니다.
  거부 목록은 본질적으로 불완전하고, 리뷰어가 그 결정을 확인할 통로가 필요합니다.

**절단 처리**
- `TruncatedCompletionError` — 파싱 **전에** 판정, 부분 응답과 usage 보존.
- `_output_budget` — 프롬프트 크기에서 산출. `_CHARS_PER_TOKEN`은 실측 하한 1.87에 맞춰
  **2.0**(낙관적 추정은 슬롯을 넘겨 불투명한 HTTP 500이 됩니다). 최소 응답 여유도 없으면
  `PromptTooLargeError`로 **거절**합니다 — 보내면 서버 장애처럼 보이는 500이 돌아옵니다.
- 재시도 사다리(0 전체 → 1 KNOWLEDGE 제거 → 2 첫 후보만)를 **단조 클램프**하고
  바깥 루프에 **레벨을 승계**합니다. 예전엔 4~6번째 생성이 1~3번의 바이트 동일 반복이었습니다.
- `BLOCK_CIRCUIT_IR`에서 `nc_pins` 제거 — 부정 지시는 7B가 무시하지만 문법은 못 어깁니다.
  `nodes.minItems`는 **1로 유지**합니다: 블록 인터페이스 넷은 한쪽 핀만 갖는 게 정상이고
  `merge_dangling_interface_nets`가 나중에 병합합니다.

**부수 수정 두 건**
- `resolve_pin_names`: 스택된 전원 이름(`U1.VDD`)을 보이는 전원핀 전체로 확장. 숨겨진 중복은
  PASSIVE로 타입되므로(STM32G474 VSS 31/47/63) 기존 `unify_stacked_pins`에 맡깁니다.
- `assign_footprints`: 해결 불가능한 풋프린트를 **지웁니다**. 존재하지 않는 이름은
  `footprint_unknown` **오류**로 빌드를 영구 차단하는데, 없으면 `footprint_missing` **경고**입니다.
  ERC 0, 연결성 정상인 보드가 레이아웃 속성 하나 때문에 통과 못 하고 있었습니다.

## 5. 남은 원인 (고치지 않음, 근거와 함께)

`unknown_module`의 MCU 블록은 프롬프트가 2,431 토큰으로 줄고 `nc_pins`가 문법상 불가능한
상태에서도 **출력 4,096 토큰을 전부 소진**합니다. 프롬프트 트리밍으로는 못 고칩니다.

원인은 부품 선정입니다. `search_parts("MCU")`는 FTS5 bm25로 **메타데이터가 짧을수록 유리**해서
`CPU_NXP_68000:MC68332`(키워드가 문자열 `"MCU 32 bit"`, 132핀)가 1위이고, `pin_count`는
4번째 정렬키라 도달하지 않습니다.

진단 워크플로의 결론을 그대로 옮깁니다: **예산 문제는 고칠 수 있고 고쳤지만, 적합성 문제는
현재 인덱스로는 고칠 수 없습니다.** `partindex`에는 출시연도·수명주기·인기도·재고 컬럼이 없고
(lifecycle 자유 텍스트는 24,232개 심볼 중 0.5%만 채워져 있으며 관련 부품은 하나도 표시 안 됨),
"모던 패밀리 허용목록"은 규칙의 탈을 쓴 하드코딩입니다.

따라서 다음 단계는 **핀 수 밴드 제한 + 부품 선정 근거를 출력에 명시**입니다:
어떤 부품을 왜 골랐는지(핀 수 포함)와 "더 나은 결과를 원하면 MCU 부품번호를 지정하세요"를
사용자에게 보여주는 것. `_ensure_named_parts`가 이미 지정 부품에 우선 경로를 주므로
이 조언은 실행 가능합니다.

## 6. 이월

- `BLOCK_CIRCUIT_IR`에 상한 있는 `nc_pins`(`maxItems: 12`) 복원 — 16핀 부품의 미사용 PWROUT
  (FT230XS `3V3OUT`)은 지금 어떤 패스도 닫을 수 없어 영구 `unconnected_pin`입니다.
- `_output_budget`을 `synthesize_ir`(평면 경로)와 `_repair`에도 적용. 평면 프롬프트는 여전히
  `max_tokens=4096` 고정입니다.
- 블록 경로 통합 테스트 — 현재 스위트의 어떤 테스트도 `agent.run`의 블록 경로에 도달하지 않습니다.
  233개가 초록이어도 위 동작들은 단위 테스트로만 고정돼 있습니다.
