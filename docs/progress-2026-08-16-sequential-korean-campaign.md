# 한국어 순차 회로 생성 캠페인 진행 기록 — 2026-08-16

## 1. 이 문서의 목적

이 문서는 회로 생성기의 최근 수정 사항만 나열하는 변경 로그가 아니다. 다음 내용을
나중에 다시 검증할 수 있도록 함께 기록한다.

- 왜 단일 프롬프트 반복 대신 여러 회로군의 한국어 프롬프트를 순차 실행하게 되었는가
- 어떤 코드를 삭제하고 어떤 공통 동작만 수정했는가
- 어떤 시도는 회귀 때문에 폐기했는가
- 자동 지표와 실제 회로도 이미지가 각각 무엇을 보여 주었는가
- 현재 어디까지 검증됐고 다음 작업의 선택 기준은 무엇인가

판정 기준은 `docs/working-rules.md`이다. 특히 특정 실패 케이스를 통과시키는 코드를
금지하고, 수정 뒤에는 이미 실행한 모든 프롬프트를 다시 실행하며, ERC 한 숫자가 아니라
부품 보존·역할 동작·근거·가독성·배선 합법성을 분리해서 본다.

## 2. 작업 방향을 바꾼 이유

이전 작업은 한 번 생성한 회로의 실패를 확인한 뒤 같은 프롬프트를 재실행하는 흐름이
반복됐다. 이 방식만으로는 다음 두 가지를 구분할 수 없다.

1. 회로 생성기 전체에 적용되는 일반적인 개선
2. 방금 본 부품명·회로명·넷 이름에만 맞춘 예외 처리

또한 특정 회로의 ERC가 줄어도 이전에 성공한 다른 회로에서 선택 부품이 사라지거나,
역할이 죽거나, 배치가 악화될 수 있다. 따라서 테스트 절차를 다음과 같이 고정했다.

1. 한국어 프롬프트 1번을 실행한다.
2. 구조화 결과, CircuitIR, ERC, compliance, 배선 지표와 렌더 이미지를 함께 검사한다.
3. 회로명이나 부품명 목록이 아닌 일반 계약 또는 측정 방법만 수정한다.
4. 1번을 다시 실행하여 이전 결과와 비교한다.
5. 1번이 회귀하지 않는 조건에서 1~2번을 실행한다.
6. 같은 방식으로 항상 1~N 전체를 재실행한 뒤 N+1로 진행한다.

즉, 프롬프트를 매번 임의로 바꾸는 절차가 아니다. 미리 고정한 서로 다른 회로군을
순서대로 넓히면서 모든 과거 결과를 재검증하는 누적 회귀 캠페인이다.

## 3. 테스트 자산 정리

### 3.1 삭제한 항목

- 처음부터 한국어로 작성할 수 있는데도 별도 변환 단계를 만든 번역 스크립트와 체크포인트
- 영문 캠페인을 생성하던 `tests/tools/build_sequential_campaign.py`
- 현재 데이터 소스 범위에서 제외된 Open Schematics 전용 adapter와 관련 테스트/import

번역 코드를 유지하면 원문과 번역본 중 무엇이 평가 입력인지 불명확해지고, 번역 로직
자체가 새로운 실패 원인이 된다. 따라서 한국어 평가 입력은 생성 스크립트의 결과가 아니라
사람이 처음부터 한국어로 작성한 고정 파일로 보존한다.

### 3.2 유지한 항목

SchGen은 제품 런타임 데이터가 아니라 연구·감사 자산으로 유지한다.

- `tests/schgen_adapter.py`
- `tests/tools/audit_schgen_corpus.py`
- `tests/tools/convert_schgen_corpus.py`
- `tests/tools/summarize_schgen_templates.py`

이 도구들은 SchGen Python을 제품 프로세스에서 실행하지 않고 AST로 정적 변환하며,
중복·프로젝트 누수·토폴로지 중복을 측정하기 위한 것이다. 순차 프롬프트를 통과시키는
런타임 템플릿 목록으로 사용하지 않는다.

## 4. 고정 한국어 프롬프트 캠페인

`tests/eval/sequential_campaign_v1.json`을 처음부터 다시 작성했다.

- 총 36개 프롬프트
- 총 30개 회로 도메인
- 자연어 설명은 모두 한국어
- `AMS1117-3.3`, `MCP6001`, `Device:LED` 같은 부품 식별자와 CAD 식별자는 번역하지 않음
- 각 항목에 순서, 안정된 ID, 회로군, 사용자가 선택한 부품, 사용자가 결정하지 못한
  설계 항목을 명시
- 수동소자, 전원, 아날로그, 타이머, 오디오, 센서·통신, MCU, 부하·모터 구동,
  계측, 배터리 등 서로 다른 토폴로지를 포함

이 파일은 생성 결과를 본 뒤 프롬프트를 고치는 용도가 아니다. 캠페인 버전 안에서는
고정하며, 프롬프트 계약 자체가 잘못된 경우에는 근거와 버전 변경을 별도로 기록해야 한다.

## 5. 순차 실행기와 회귀 판정

`tests/benchmarks/run_sequential_campaign.py`를 추가했다. 실행기는 1~N을 같은 조건으로
실행하고, 각 케이스를 이전 실행의 같은 케이스와 비교한다.

현재 저장하는 항목은 다음과 같다.

- 실행 단계와 회로도 생성 여부
- connectivity 결과
- self ERC 오류와 경고
- KiCad ERC 위반 수
- visual issue 수
- 실제 wire 사용 비율
- compliance 오류 수
- 요청 역할 중 실제로 동작하는 역할 수
- 사용자가 선택한 부품의 보존/유실 목록
- 생성된 CircuitIR hash
- exact 전사 케이스의 경우 명시 회로와의 차이

회귀 판정은 이전에 참이던 draft/connectivity가 사라지는 경우, 오류·경고·시각 문제가
늘어나는 경우, 배선율이나 동작 역할 수가 감소하는 경우, 새 선택 부품 유실이 생기는
경우를 각각 보고한다. 회로도 자체가 생성되지 않은 과거 실행은 compliance를 수행할
대상이 없으므로 오류 0으로 간주하지 않고 `null`로 기록한다. 과거 `0`과 새 회로의 실제
오류 수를 비교해 거짓 회귀를 만들던 문제도 이 기준으로 수정했다.

## 6. 이번 단계에서 채택한 일반 수정

### 6.1 정확한 KiCad 심볼 ID 보존

`Library:Symbol` 형태의 완전한 ID는 suffix 길이와 무관하게 정확한 식별자로 취급한다.
예를 들어 `Device:LED`를 요청했으면 부분 문자열 유사도가 아니라 대소문자를 무시한
완전 일치로 보존 여부를 판정한다.

이 수정은 LED라는 특정 부품 예외가 아니라 모든 KiCad full library ID에 적용되는
식별 계약이다. 관련 구현은 `src/circuitgen/compliance.py`, 회귀 테스트는
`tests/test_compliance.py`에 있다.

### 6.2 패키지와 부품 역할의 분리

LLM이 `SOT-223` 같은 패키지 문자열을 별도의 주문 부품 또는 기능 역할로 반환하는
경우가 있었다. 이를 부품명 목록으로 제거하지 않고 기존 footprint 문법 해석 결과를
사용해 판정한다.

`Agent._normalize_physical_roles()`는 다음 공통 규칙을 적용한다.

- 표준 footprint 제약만 표현한 항목은 BOM 역할에서 제거한다.
- `2-pin header`, `2x3 connector`처럼 값이나 설명에 있는 접점 형상을 일반적인
  `header`/`connector` 검색어에 복원한다.
- 특정 회로명, 특정 제조사, 특정 프롬프트 단어 목록을 사용하지 않는다.
- `_ensure_named_parts()` 뒤에 실행하여 부품 보존 단계가 패키지를 다시 역할로 만든
  경우도 같은 규칙으로 정리한다.
- 두 번 실행해 결과가 달라지지 않는 멱등성을 테스트한다.

`requested_part_numbers` 역시 동일한 footprint 문법을 사용해 순수 패키지 토큰만
제외한다. 실제 주문 부품번호까지 삭제하지 않는 테스트를 함께 추가했다.

### 6.3 잘못된 스키마 확장 폐기

한 차례 `RequirementSpec`의 일반 설계 항목에 `package` 필드를 넓혀 물리 정보를 직접
받는 실험을 했다. 결과는 개선이 아니었다.

- LED에 SOT-223가 붙음
- 버튼에 0805가 붙음
- 1번 회로의 wired ratio가 1.0에서 0.5로 하락
- 2번 회로에서 compliance 오류가 증가

이는 모델이 빈 물리 필드를 정확히 채운 것이 아니라 그럴듯한 패키지를 환각한 결과다.
따라서 해당 스키마와 프롬프트 변경은 전부 되돌렸다. 최종 구현은 모델 출력 공간을
늘리지 않고, 이미 있는 물리 표현을 결정론적으로 정규화하는 방식이다.

## 7. 순차 실행 결과와 이미지 판독

중간 산출물은
`tests/artifacts/benchmarks/sequential/ko-step-002-physical-role-v2/report.json`, 최신 누적
산출물은 `tests/artifacts/benchmarks/sequential/ko-step-003-header-geometry/report.json`에
있다.

### 7.1 1번: 5V 버튼·LED 회로

자동 지표에서는 다음 결과가 나왔다.

- draft 생성 및 connectivity 통과
- self ERC 오류 0
- KiCad ERC 위반 0
- visual issue 0
- wired ratio 1.0
- compliance 오류 0
- 요청 역할 4/4 동작
- `Device:LED`, `Switch:SW_Push` 보존

`ko-step-002-physical-role-v2` 렌더 이미지를 직접 판독했을 때 요청한 입력 커넥터는
1x2인데 도면에는 1x4 커넥터가 배치돼 있었다. 이 관찰을 일반 측정 계약으로 바꿔
`compliance.check_connector_geometry`를 추가했다. 요청 행·열·접점 수, 실제 심볼 핀 수,
footprint pad 수와 동일 형상의 수량까지 분리해서 기록한다. 이후 실행에서는
`Connector_Generic:Conn_01x02`와 2-pad footprint가 선택돼 형상은 일치했다.

그러나 최신 1~3번 누적 실행에서는 역할 동작이 4/4에서 3/4로 줄고 D1 단락이 확인됐다.
따라서 커넥터 형상 개선과 회로 전체 개선을 동일시하지 않았으며 1번은 여전히 실패다.

### 7.2 2번: AMS1117-3.3 선형 전원

중간 실행의 자동 및 이미지 검사에서 모두 실패가 확인됐다. 최신 누적 실행에서는
더 큰 회귀가 발생했다.

- draft와 connectivity는 생성됨
- self ERC 오류 28
- KiCad ERC 위반 20
- visual issue 1
- compliance 오류 11
- 요청 역할 5개 중 1개만 동작
- AMS1117-3.3 자체는 보존
- 레귤레이터 입력 핀이 전원 rail에 연결되지 않음
- 커패시터 두 개와 레귤레이터가 죽거나 부유함
- A2 크기의 지나치게 긴 수평 배치와 중복 커패시터가 보임
- +3V3 rail 심볼이 사라짐

다음 작업을 "AMS1117 회로 수정"으로 정의하지 않는다. 그렇게 하면 이 케이스에만
맞는 연결 규칙을 넣을 위험이 크다. 현재 먼저 확인된 공통 평가 공백은 1번에서도
드러난 물리 접점 계약은 이제 측정되고 있다. 다음 공통 평가 공백은 특정 레귤레이터가
아니라 전원 입력 핀이 요청 rail까지 실제로 전도되는지를 여러 전원 회로군에서 측정하는
것이다.

### 7.3 3번: MCP6001 비반전 증폭기

1~3번 누적 실행에서 처음 생성됐다.

- draft와 connectivity 통과
- MCP6001 보존
- self ERC 오류 0, 경고 1
- KiCad ERC 위반 0
- visual issue 0
- wired ratio 1.0
- compliance 오류 0
- 요청 역할 7개 중 3개만 동작 판정

이 케이스는 이전 동일 케이스 실행 결과가 없어 전후 개선을 주장할 수 없다. 피드백과
바이패스 역할 일부는 현재 이름만으로는 동작을 검증할 수 없다. ERC 0을 완성도 근거로
쓰지 않고, 역할 동작 측정의 공백으로 기록한다.

## 8. 검증 상태

최종 실행 명령과 결과는 다음과 같다.

```text
git diff --check
.venv/bin/pytest -q

354 passed, 1 warning in 201.63s
```

경고 1건은 기존 FastAPI/Starlette TestClient의 httpx deprecation이다. 이번 변경으로
추가된 테스트 실패는 없다. 단위 테스트 통과는 코드 계약의 회귀가 없다는 증거일 뿐,
36개 회로 생성 품질이 검증됐다는 의미는 아니다. 이 결과는 커넥터 계약 추가 전의 전체
회귀 결과이며, 현재 순차 캠페인의 최신 생성 범위는 1~3번이다. 커밋 전 현재 HEAD의
전체 테스트를 다시 실행해 최종 숫자를 별도로 확인한다.

## 9. 다음 작업

다음 단계는 아래 순서로 진행한다.

1. 전원 입력 핀이 요청 rail에 실제로 전도되는지를 측정하는 일반 계약을 정의한다.
   특정 레귤레이터 이름이나 실패 프롬프트 문자열은 사용하지 않는다.
2. 서로 다른 전원 회로군에서 같은 지표가 깨지는지 확인한 뒤에만 생성기를 수정한다.
3. 생성기 수정 전후에 1~3번을 모두 재실행한다.
4. 회귀가 없으면 1~4번으로 넓혀 NE555 계열에서도 동일 지표를 수집하고 이미지를 판독한다.
5. 이후에도 항상 1~N 재실행 → 이전 결과 비교 → N+1 추가 순서를 유지한다.
6. 실패 회로 이름이 아니라 여러 회로군에서 반복되는 제품 지표의 부족을 기준으로
   다음 수정 대상을 고른다.

SchGen 4,167개 변환 후보와 1,694개 고유 토폴로지는 별도의 데이터 감사 트랙이다.
검증되지 않은 SchGen 빈도나 코드를 곧바로 제품 설계 규칙으로 승격하지 않으며,
KiCad 10 심볼·핀 결합, 왕복, 렌더, 출처와 사람 검토 게이트를 통과한 뒤에만 데이터셋
확장 또는 QLoRA 판단에 사용한다.

## 10. 완료로 오해하면 안 되는 사항

- 36개 프롬프트를 만들었다고 36개를 모두 검증한 것은 아니다.
- 1번의 ERC 0은 완전 통과가 아니다. 커넥터 형상은 고쳐졌지만 역할 회귀와 LED 단락이 있다.
- 2번의 부품 보존은 기능 동작 성공이 아니다. 레귤레이터가 전기적으로 고립됐다.
- 3번의 compliance/ERC 0은 역할 7개가 모두 동작한다는 뜻이 아니다.
- SchGen 전체 행을 감사·변환 입력으로 사용한다는 것은 전부를 동일 가중치의 학습
  정답으로 사용한다는 뜻이 아니다.
- 현재 단계는 회로도 생성까지다. PCB 배치, 동박 자동 라우팅, PCB DRC 최적화는
  작업 범위에 포함하지 않는다.
